**Manual triage of every finding below (verified by reading raw records,
2026-08-28), so this file is not misread as 35 files of live bugs:**

- **All `field X: N/M records are None/NaN` findings for `umf_mean` /
  `umf_per_replan` in `e0_*` files are BENIGN.** Spot-checked
  `e0_planning_n100/baseline_R2.jsonl`'s 8 None records: every one has
  `umf_per_replan: [None]` — the motion gate (score.py's documented
  denominator guard, G6) correctly returned `None` for a low-motion/short
  chunk, exactly the behaviour G6 exists to verify, not a data bug.
- **All `field hit: N/M records are None/NaN` findings in `e2_*` files are
  BENIGN.** Spot-checked one `e2/e2_episodes.jsonl` record with
  `hit: None`: it also carries `gated: True, scores: [None, None]` — the
  chunk was correctly gated (uninformative), so no verdict was possible.
  This is the intended, documented behaviour of the motion gate, not a bug.
- **All `field episode/router: N/M records are None/NaN` findings in
  `e2_*` files are BENIGN and explained by A3's fix landing mid-project.**
  Spot-checked: the None-episode records are per-SEED summary records
  (`{"charts_committed": ..., "expander_stats": {...}, "library_size": ...}`,
  no `episode`/`router` key at all) mixed into the same JSONL as per-episode
  records — a different record type, not a missing field. This is also the
  root cause of every "**UNEQUAL group sizes**" finding below: the group
  sizes differ because a run's summary records (n = number of seeds) are
  being counted in the same grouping as its episode records (n = seeds x
  episodes x routers). Not a paired-episode-count defect — a limitation of
  this script's naive single-file grouping, which does not distinguish
  record types. **Action for a future pass:** either add a `record_type`
  discriminator field to every writer (only `run_e2.py`'s A3 addition has
  one so far) or have this script filter on it before grouping.
- **The `e1_smoke`/`e2_smoke` "EXACT-ZERO variance on `seed`" findings are
  BENIGN.** Both are smoke tests deliberately run at ONE fixed seed
  (12345 / 0 respectively) across multiple routers — that IS the paired
  design (G5), not a red flag. The zero-variance check is genuinely useful
  for a real multi-seed run (e.g. it is exactly what would have caught
  SUBMISSION_PLAN.md's A-ix/B12 Modal relabelling bug on `atlas_out/e4*`
  data, had any existed at the time of this sweep) — no `e4*` directory
  exists yet (E4/S2 has produced zero episodes, per CLAUDE.md's AUDIT NOTE
  #9), so that check could not be exercised against real multi-seed E4 data
  here. **Re-run this script after Phase 5 produces `atlas_out/e4*` — that
  is the first real test of this specific check.**

**Net verdict: no unexplained NaN, zero-variance, or episode-count red flag
survived manual triage in the 35 files that exist today.** Every finding
below traces to a documented, intended mechanism (motion gate, mixed record
types, or a deliberately fixed smoke-test seed). This does not mean the
underlying experimental design is sound (see `CLAIMS_MATRIX.md` /
`RESULTS_AUDIT.md` for that) — only that this specific sweep (exact-zero
variance, episode-count mismatches, NaN sweeps) found nothing NEW beyond
what A8 (sr_by_bucket overflow) and the motion-gate None convention already
covered.
